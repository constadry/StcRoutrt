# StcRoutrt

Маршрутизатор: регистрирует шаблоны вида `/foo/bar/{p:int}/` и по строке `/foo/bar/5` вызывает нужный обработчик с уже разобранными параметрами.

## Как работает

Все маршруты хранятся в дереве (trie). Один узел дерева соответствует одному сегменту пути между `/`.

У каждого узла есть:
- `Static` — словарь детей для обычных сегментов (`foo`, `bar`);
- `Param` — один ребёнок для любого параметра (`{p:int}`, `{id:guid}`);
- `Handler` — обработчик, если на этом узле заканчивается маршрут.

Например, после регистрации `/foo/bar/{p:int}/` и `/sum/{a:int}/{b:int}/` дерево такое:

```
(корень)
 ├─ foo
 │   └─ bar
 │       └─ {param}  → обработчик
 └─ sum
     └─ {param}
         └─ {param}  → обработчик
```

**Регистрация.** Шаблон режется по `/`. Идём от корня: обычный сегмент ищем в `Static` (нет — создаём), сегмент в `{}` уходит в `Param`. На последнем узле сохраняем обработчик. Если обработчик там уже есть, это дубль, бросаем исключение.

Типизированные `RegisterRoute<T1>` и `RegisterRoute<T1, T2>` один раз заворачивают `Action` в общий обработчик `Func<string[], bool>`. Он разбирает строки через `T.TryParse` (`IParsable<T>`, `InvariantCulture`) и возвращает `false`, если параметр не подошёл по типу.

**Поиск (`Route`).** Строка режется по `/`, и мы идём по дереву: сначала пробуем точное совпадение в `Static`, иначе уходим в `Param` и запоминаем значение сегмента как параметр. Дошли до конца и на узле есть обработчик — вызываем его со значениями параметров. Не нашли — пишем «Маршрут не найден».

## Почему хорош при большой нагрузке

- **Скорость не зависит от числа маршрутов.** Поиск делает по одному обращению к словарю на каждый сегмент пути. Для `/foo/bar/5` это три шага, будь в роутере 10 маршрутов или 10 000. Перебора всех шаблонов и регулярных выражений нет.
- **Вся тяжёлая работа сделана при регистрации.** Шаблон разбирается один раз, обёртка с парсингом типов создаётся один раз. При вызове остаётся пройти по дереву и сделать `TryParse`.
- **Чтение без блокировок.** `Route` ничего не блокирует, а `ConcurrentDictionary` читается без локов, поэтому тысячи потоков могут вызывать `Route` одновременно и не ждут друг друга.
- **Регистрация потокобезопасна.** `RegisterRoute` выполняется под `lock`, так что одновременная регистрация не испортит дерево и не пропустит дубль. Регистрация редкая, поэтому этот lock на нагрузку не влияет.
- **Нет исключений на плохом вводе.** Неверный параметр (`/foo/bar/abc` для `int`) даёт `TryParse == false`, а не `FormatException`. Исключения в .NET дорогие, и под нагрузкой это важно.

Что ещё можно ускорить: `Route` выделяет память на `Split` и массив параметров при каждом вызове; это можно убрать разбором через `ReadOnlySpan<char>`.

## Что осталось из дополнительных требований

**Передача параметров по имени, а не по порядку.** Сейчас значения передаются в обработчик в том порядке, в каком параметры стоят в пути. Нужно, чтобы для шаблона

```csharp
r.RegisterRoute<int, int>("/{b:int}/bar/{a:int}/", (a, b) => ...);
```

вызов `/1/bar/2` дал `a = 2`, `b = 1`, то есть каждое значение бралось по имени параметра лямбды.

Как сделать (всё один раз при регистрации, на скорость `Route` не влияет):
1. При разборе шаблона запомнить имена параметров по порядку в пути: `["b", "a"]`.
2. Взять имена параметров делегата: `action.Method.GetParameters()` → `["a", "b"]`.
3. Построить перестановку «позиция в делегате → позиция в пути»: `[1, 0]`. Если какого-то имени в шаблоне нет, бросить исключение при регистрации.
4. В обёртке брать `args[map[0]]` для первого параметра и `args[map[1]]` для второго.
